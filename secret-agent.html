A tool-calling agent with no framework under it. The loop is 53 lines including its error handling. Everything else exists because that loop breaks in exactly 4 ways, and it was built against a small local model on purpose, since a small model emits messy output and messy output is what forces the interesting code to exist. No LangChain, no LlamaIndex.

The loop

The model asks for a tool, my code runs it, the result goes back

That repeats until the model stops asking. The stop condition keys off the absence of a tool call, not the presence of prose, because small models narrate ("Sure, let me check that file.") while also emitting the call, so stopping on text ends every run on iteration 1. The 4 failure modes below are the whole design.

Runaway. The model calls tools forever. Hard cap at 15 iterations, then it raises rather than returning the last partial text, because a run that hit the cap failed.
Malformed call. JSON that is not JSON: fenced, single-quoted, trailing commas, double-encoded args. A repair ladder plus bounded retry, then raises.
Tool blows up. An exception inside a tool is caught and returned to the model as a readable error, so a wrong filename is a normal Tuesday, not a crash.
Context overflow. The payload exceeds the window. Counted before every call, because Ollama returns HTTP 200 and silently drops the middle of the history.

Built against a small model on purpose

A frontier model hides bad tool calls behind constrained decoding. Building against llama3.1:8b is what forces parse, validate, retry to be real rather than aspirational.

An external review broke the sandbox

python was on the bash allowlist, so python3 -c 'open(...)' wrote outside the root, and bash never called path confinement at all. Both fixed, both with regression tests, all in REVIEW-2026-07-25.md.

Retrieval is a tool, not a preprocess

The model decides whether to search, reformulates the query, and can search twice for a two-part question. A preprocess step retrieves once, on the original wording, for every question including "thanks".

What I measured, including against myself

The numbers that went against me are the point

Every figure in the repo is reproducible from a script, and the parser records every repair it applies, because it sits between the model and every measurement you could take of the model.

The parser gap looks like a capability gap, and is not. On the same 10-task set, llama3.1:8b emitted clean JSON on every call while qwen2.5-coder:7b needed repair on 70%. Benchmark them with fence-stripping off and qwen scores about 70% worse, which would be entirely my parser. Repair rate is a property of the specific model, not of model size, and that was not what I expected going in.
Retrieval is honest about its weak half. hit@3 is 0.90 across 20 pairs, but split by phrasing it is 1.00 when the question uses the document's own words and 0.71 when it does not. Reporting only the 0.90 would have hidden the second row. Chunk-size and embedding-prefix ablations both earned their place by contradicting a claim I had already written into a comment.

Why a local 8B model instead of an API

The messy output is the whole point

Small local models produce bad tool calls: fenced JSON, single quotes, trailing commas, arguments double-encoded as a string, invented key names, tool names that do not exist, and my favourite, a response that emits the tool call and then narrates the result it expects before the tool has run. A frontier model hides most of that behind constrained decoding, so building against the messy one is what makes the repair ladder, the stop condition and the context budget real rather than decorative. The provider sits behind a one-method interface, so swapping in a hosted model is one file, not a rewrite. The measurement caveat is in the repo: on the tasks I ran, both llama models emitted clean JSON every time, and the repair ladder got claimed hard on exactly one model, which is the argument for having it and for always printing the rate.
