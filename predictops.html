PredictOps

Most ML job listings ask for Docker, FastAPI, CI/CD, MLflow, and almost never for a novel model. So the model here is a plain tabular churn classifier, and the work went into the ops loop around it: a training comparison, a validated API, a slim container, a CI gate that blocks a bad model, registry promotion, and PSI drift detection.

The pipeline

Train, compare, serve, containerize

A single sklearn Pipeline (impute → scale numeric → one-hot encode categorical → classifier) so preprocessing can never leak test data into training. Logistic Regression and XGBoost both run 5-fold stratified CV, the CV ROC-AUC winner gets logged to MLflow and saved, and FastAPI loads it behind validated request and response models.

The simpler model won. Logistic Regression beat XGBoost on 5-fold CV ROC-AUC, 0.846 to 0.842, and held the edge on the held-out test too (0.842 vs 0.837). The pipeline serves whichever model wins, so this was the measured outcome, not a tidy pick.

The churn model is plumbing

All the depth sits after it: a CI gate that fails the build below 0.80 ROC-AUC, registry promotion, and drift detection wired into one make pipeline.

The simpler model won, and shipped

Logistic Regression beat XGBoost on cross-validated ROC-AUC, 0.846 to 0.842, so the simpler model is the one that got promoted. I did not go in expecting that.

A tiny serving image, on purpose

A multi-stage build trains and exports to ONNX, then serves with onnxruntime alone, no sklearn at runtime. That takes the image from about 1.17 GB to 343 MB.

Try it

Inject drift, watch the gate block deploy

The drift gate runs on PSI with a 0.15 per-feature limit. Flip the switch to shift a feature out from under the model and watch the run stop before promotion. Runs in your browser, no server.

Where it stands

All 7 phases shipped.

Built one phase at a time, each committed on its own. What is in the repo:

PhaseStatus
0 · Repo scaffolddone
1 · Training + MLflowdone
2 · FastAPI servingdone
3 · Multi-stage Dockerdone
4 · CI eval gatedone
5 · MLflow registry + promotiondone
6 · Evidently drift detectiondone
7 · Wire the full loopdone
Phase 4 was the centerpiece. A GitHub Actions workflow lints, tests, then asserts ROC-AUC ≥ 0.80 or the build fails, the same way a broken unit test does. Proven by shipping a deliberately degraded model, watching CI go red, then fixing it to green.
Phase 5-6: registry promotion and a real PSI drift check. The winning run registers in the MLflow registry and promotes Staging → Production. Drift runs Evidently with PSI (Population Stability Index) as the per-column stattest, comparing a reference split against a shifted "current" split, and alerts when any feature's PSI exceeds 0.15.
Phase 3: multi-stage Docker that earns the name. The first pass copied the whole build environment (MLflow, Evidently, pytest, ruff) into the runtime image. Splitting serving-only dependencies out cut the served image from 1.17GB to 343MB, a 71% reduction measured off a real build.

Why it exists

The model is the boring part on purpose

My other 2 projects are LLM research. This is the breadth piece beside them: a plain churn classifier so nobody mistakes the domain for the point, wrapped in the ops loop most portfolios skip. A leakage-safe pipeline, a validated API with a health check, a container that ships only what it serves, and a CI gate that fails a bad merge. The full loop runs end to end with one command.
