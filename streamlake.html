StreamLake

Most pipelines fail silently: the job succeeds, the dashboard renders, and the number is wrong because a vendor changed a column or last night's load only got half the rows. StreamLake puts a data contract next to every table, checked before the next hop is allowed to read. One month of NYC taxi trips moves through bronze, silver, gold, dbt and a Kafka arm, and every hop asserts what must hold and stops the run when it does not.

A contract at every hop

7 contracts, 47 checks, run before the next hop reads. An error breach raises and stops the DAG; a warn breach is recorded and surfaced. Last run: 0 errors, 2 warnings.

Quarantine is not failing

Individual bad trips (fares of −$300, dropoffs in 2098) are moved to silver.trips_quarantine with the rule that rejected them. The run fails only if quarantine swallows more than 10% of the month.

One scan, not N

Every check compiles to a Spark aggregate expression, merged into one df.agg. Silver's 14 assertions over 2.9M rows cost one pass, about 2 seconds. A test asserts the single pass.

Why it holds up

3 decisions in the engine worth stating

Error stops, warn surfaces. A breach at error severity raises and the DAG halts, so the warehouse keeps serving yesterday's correct data instead of today's broken data. A warn breach is logged and shown on the dashboard.
Freshness is measured against the logical run time. A backfill of January 2024 data is not stale because it ran in 2026. The assertion is that the data covers its own period, not the wall clock.
dbt recomputes Spark's gold aggregate. The same daily number is built twice, in Spark and in warehouse SQL, and a parity test fails the build if the two engines disagree by more than a cent. The duplication is the reconciliation.
The stream arm misbehaves on purpose. The producer sends 5% of events twice and 3% late. The consumer's 2-minute watermark and dedup removed exactly the 182 injected redeliveries: 4,182 produced, 4,000 counted.

Status

What actually ran

The batch spine, the Kafka arm, dbt on DuckDB, an Airflow DAG (9 tasks, 66s) and a Kubernetes consumer on kind have all run on a laptop, for free, off the numbers in this repo. The same code points at S3, a real Kafka and Snowflake by changing environment variables, nothing is hardcoded to the local setup. The Snowflake path is written but has not been run against a live account.
