Vaultex

A payments service that cannot double-spend and cannot lose a cent to a retry. Every transfer posts one debit and one credit of equal amount inside a single database transaction, so the whole ledger nets to zero and any balance can be rebuilt from it. The interesting part is not the happy path. It is what happens when 50 threads spend the same money at once, when a load balancer replays the same request 20 times, and when the shipped fraud model turns out to be honestly useless.

The transfer path

One transfer, one transaction, one debit and one credit

A request carries an X-Api-Key and an Idempotency-Key. If the key was seen before, the service returns the stored outcome instead of moving money again. If it is new, a separate TransferExecutor bean opens a fresh transaction, checks status, currency and funds under an optimistic version lock, scores the amount for fraud in the same JVM, then writes the debit, the credit, both cached balances and the audit row as one commit. Everything happens together or nothing does.

The version check is what stops the overdraft, not the balance read. In the 50-thread race, every thread reads a balance that says yes. Exactly 25 post and exactly 25 fail with INSUFFICIENT_FUNDS, the source lands on 0.00, and the ledger holds exactly 50 entries. Delete @Version and rerun: all 50 post, and an account funded with 250.00 records 500.00 leaving it.

One commit or none

The transfer row, both ledger entries, both cached balances and the audit row commit together. The 4 invariants hold across every row, checked by an @AfterEach on every money-moving test.

The fraud branch is a no-op on the ledger

A score at or above 0.85 returns 422 BLOCKED_FRAUD, writes an audit row, and posts nothing. The block path is auditable even though the model behind it should not decide anything.

Balances rebuild from the ledger

GET /reconciliation recomputes every balance as opening balance plus the signed entries. Across a load run it rebuilt 100 accounts from 113,046 entries with zero drift.

Three things worth knowing

What has teeth, and what is honest about not working

One unique index closes the retry window. 20 copies of one transfer arrive at once, and the account can afford all 20. Exactly 1 transfer row is written, 25.00 moves rather than 500.00, and all 20 responses carry the same transfer id. Drop the UNIQUE (idempotency_key) constraint and all 20 post as distinct transfers.
The fraud model ships broken, on purpose. Its honest AUPRC is 0.0041, against 0.784 for a reference model built on the ULB features no live system can compute. At the shipped threshold it blocks 169 legitimate transfers for every fraud it catches, so 99.99 is blocked and 100.00 posts. It is wired in to demonstrate the inline scoring and the audited block path, not to decide anything.

Why this project exists

The correctness is the whole point

Most portfolio payment demos post to a balance column and call it done. This one is built around the two failures that actually cost money: spending the same balance twice, and paying twice for one retried request. Both are proven by tests that run 3 times per build against a real PostgreSQL 16 started by Testcontainers, because a concurrency test that only passes once has told you almost nothing, and the assertions check the exact split rather than roughly half. The fraud model is included with the same honesty. It measures its own AUPRC on a split that does not leak, reports that the number is near zero, and says out loud that the right posture for a control this weak is a human review queue, not an automatic block.
